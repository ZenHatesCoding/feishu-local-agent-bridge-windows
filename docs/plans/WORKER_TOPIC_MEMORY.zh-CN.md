[Worker 话题记忆](../WORKER_MEMORY.zh-CN.md)。第二台机器的飞书验收仍须独立完成，不能用本机测试代替。

## 1. 要交付的能力

每个 Worker 独立保存完整的授权记录，并为每个话题维护可更新、可追溯、长度受控的记忆。
Agent 重启、模型会话更新或执行电脑变化后，可以利用自己的记忆继续工作；需要精确细节时，
能从摘要逐层找到原文。系统自动执行加载、预算检查、整理调度和可靠保存，不依赖 Agent
偶尔想起某条提示词。

这里的完整指该 Worker 实际收到、执行或获准取得的内容。飞书没有投递的消息不会凭空出现；
缺失历史应显式记录为未知或缺口。完整记录不意味着采集秘密、私有思维链或其他 Agent 的会话。

第一版交付必须同时满足：

1. Worker 可独立部署，机器上不需要本地 Hub，也不需要其他 Worker 的目录。
2. 每 Worker、每话题有自己的完整账本和派生记忆，允许内容重复。
3. 每次执行自动获得当前任务记忆、受控历史和检索工具。
4. 超预算会自动整理；失败不会删除原文，也不会把机械截断记作成功摘要。
5. 用户更正、决定撤销、未完成事项和关键证据能持续保留或准确回查。
6. 重启、重复事件、并发和中断不造成重复记忆或新状态被旧运行覆盖。
7. Agent 名称、角色和安装位置不影响能力；各种宿主分别适配、分别验收。

不能承诺任意长历史都能以固定 token 无损进入模型。承诺是：原文可恢复、关键任务状态有明确
保留规则、当前提示词有界、覆盖缺口可见，并以实际回忆和续作任务验证效果。

## 2. 设计依据与取舍

本设计借鉴已有机制，独立定义符合本项目的运行协议和数据模型，不依赖任何候选项目作为必装运行时。

| 借鉴来源 | 采用的思路 | 本项目的处理 |
| --- | --- | --- |
| lossless-claw | 原文与摘要分离、分层来源关系、预算组装、展开召回 | 以飞书话题贯穿新模型会话；摘要失败保留待处理状态 |
| memU | 宿主 Agent 自己整理、prepare/commit、按宿主适配 | 每个 Worker 独立配置、存储和安装，不要求共享 backend |
| Claude-Mem | 生命周期接入、索引到详情的渐进读取 | 以话题而非 cwd/代码项目作为默认边界 |
| Hermes / Letta | 有界工作记忆、Agent 编辑、维护运行、版本恢复 | 明确区分当前状态、历史摘要与宿主原生全局记忆 |

具体来源及核对提交见第 18 节。本文中的模块、接口、默认预算和验收要求是新的设计决定，
不是对这些项目现有能力的转述。

## 3. 部署和责任边界

部署有 Hub 与 Worker 两种职责。`role: all` 只是两者共置；本机 Worker 不获得读取 Hub
数据库、其他 profile 或其他 Worker 文件的特权。

一个 Worker 安装可以承载多个独立 Agent 实例。以下每个记忆实例归属于一个逻辑 Agent 执行身份，
不是某个短命进程，也不是 `codex` 等 adapter 类型。两个 Codex Bot 同样可以完全独立运行。

```text
飞书与远端 Hub
       │ 授权事件、dispatch、结果与 Artifact 引用
       ▼
Worker 的 Bridge / Hermes Hook
       ├── 当前 Agent runtime 与原有登录
       └── 本地记忆运行层
             ├── 完整授权账本
             ├── 当前任务状态
             ├── 历史摘要与来源索引
             └── 检索、预算、整理队列、恢复
```

Hub 继续负责任务身份、负责人、dispatch、授权与共享 Artifact。记忆模块不新增 Hub API，
不改变协作授权，不把摘要、记忆版本或整理调度塞进中央账本。

每个 Worker 的维护推理使用自己的 Agent/模型配置和认证。数据与工具均在本地，模型服务可以仍是
该 Agent 配置的远端服务；Worker 自治不意味着模型离线运行。

## 4. 身份和话题边界

逻辑身份分三层：

- `deploymentId`：本次协作部署的稳定标识，区分相同飞书环境中的不同安装。
- `workerInstanceId`：逻辑 Agent 实例的稳定标识，首次安装生成并保存在本地；重启不变。
- `conversationKey`：`channel + tenantKey + chatId + threadId`。

`memoryScopeId` 由上述身份规范化后计算哈希。显示名、模型名、cwd、PID、provider session ID
不参与话题连续性判断。用户把 Bot 改名、切模型、换工作目录，不会自动丢失记忆。

飞书话题保留稳定 threadId。普通无话题群使用群 scope，并明确其边界更粗；私聊使用单独 scope。
话题连续性跨每轮新 provider session 保持。Hub taskId 和 dispatchId 记录为关联信息，不能替代
Worker 的本地话题身份；实际 Hub 控制状态以本轮查询结果为准。

Worker 搬迁通过显式备份恢复保留逻辑身份，节点路径重新绑定。复制成新 Bot 时生成新实例身份，
历史导入带来源标记。运行两个同身份副本的执行授权问题由现有调度处理；本方案不声称本地记忆锁
可以解决跨电脑的重复 dispatch 执行。

## 5. 三类数据，各自独立演进

### 5.1 完整账本：可回溯的事实记录

保存入站消息、自己的最终结果、Artifact 引用、必要的执行结果证据、修正关系及实际投递状态。
消息文本保留获准内容，不在摄入时先总结后丢弃。大文本以内容寻址 blob 保存，账本记录哈希和长度。
附件记录内容哈希、来源 locator 和本机 materialization；大型二进制不自动进入模型。

不把原始 thinking 事件、认证信息和所有工具输出无差别存入任务账本。执行证据可以是“测试命令、
退出状态、结果摘要、日志引用”；模型报告的成功与工具实际证实的成功使用不同证据等级。

每个 topic 使用本地递增 `seq`，另保存来源事件 ID、发送时间与观察时间。重放按已提交 seq 稳定
推进；迟到事件保留原始时间，在新 seq 追加，不悄悄改写已整理的顺序。重复消息依来源 ID 幂等；
编辑和删除生成更正事件，而非凭内容哈希误删两条相同但合法的消息。

### 5.2 当前任务状态：每轮继续工作所需的记忆

状态由 Agent 更新，存为结构化条目和版本快照，按预算渲染为可读文本：

| 条目 | 记录什么 |
| --- | --- |
| 目标 | 当前目标、阶段和验收条件 |
| 约束 | 用户要求、禁令、固定参数；保留重要原文 |
| 决定 | 已采用方案，以及后来撤销或替换关系 |
| 进展 | 已完成工作、验证状态、尚未交付的结果 |
| 待办 | 未完成事项、阻塞、下一步、长期挂起事项 |
| 证据 | 关键文件、提交、Artifact 和原文位置 |
| 假设 | 待验证判断和争议，不混写成既定事实 |

通用条目字段：`itemId, kind, text, status, sourceRefs, evidenceLevel, supersedes`。
有效状态至少区分 active、resolved、superseded、disputed、parked。更新通过新增/替换/结束条目表达，
不依赖模型每轮重写整份自由文本，也不要求为一次短聊填满全部栏目。

来源等级区分 human-explicit、agent-reported、tool-observed。它表达来源，不自动证明内容真实。
例如另一位 Agent 的“测试已通过”仍是报告，除非有相应验证证据。模型无法自行将报告升级成工具证据。

`parked` 是有索引可查的挂起状态，不等于完成。当前执行相关的未完成工作必须可见；大量无关挂起项
通过按阶段/主题分页索引保留，并显示未展开数量，避免列表静默消失。

### 5.3 历史摘要：可展开的阶段记录

对已结束片段生成叶摘要，叶摘要连接原始事件；更高层摘要连接下层摘要。节点包含时间范围、
覆盖 seq、核心内容、被省略细节的检索提示、来源子节点和生成版本。旧原文始终保留。

按相邻事件范围归并，避免完全靠关键词把不同阶段混成一个摘要。纠正旧决定时，当前状态明确标记
旧项已失效；历史摘要保留“当时怎样决定”，查询时同时返回相关后续更正，防止旧事实被当成当前事实。

两种记忆不是同一份文本反复压缩：当前状态维护有效事实，历史摘要保留过程和证据导航。长期总结
不以不断压缩同一份旧摘要作为唯一输入；重建时可回到叶摘要或原文。

## 6. 本地持久化

每个逻辑 Agent 实例拥有自己的根目录，不使用机器全局共享记忆数据库：

```text
<worker-state>/memory/
  identity.json
  memory.sqlite
  blobs/<sha256>
  skills/<host-specific-install-assets>
  backups/
  jobs/<job-id>/
```

SQLite 保存权威事件、状态快照、摘要关系和维护进度；FTS 是可重建索引。Markdown 和 JSONL
可以导出、备份、提供给 Agent 或人工检查，不维持需要跨文件事务的多份可写真相。
磁盘冗余允许，选择事务存储的理由是中断和并发正确性，而非节省账本副本。

建议表：

| 表 | 核心约束 |
| --- | --- |
| topics | 唯一 scope、nextSeq、可见的历史缺口、最后活动时间 |
| events | `(topicId, seq)` 主键；来源 ID 唯一；文本或 blob 引用 |
| source_links | 事件的外部来源、Artifact、修正关系 |
| state_revisions / state_items | 不可变版本和结构化任务条目 |
| summaries / summary_sources | 摘要节点及事件/子摘要来源关系 |
| context_projections | 每次运行实际使用的版本、事件范围、预算与省略清单 |
| maintenance_jobs | 目标范围、baseRevision、输入哈希、状态、失败原因和重试 |
| topic_leases | 本机跨进程写协调、到期与 fencing generation |
| search_index | 原文、状态、摘要的可重建全文索引 |

正文按 scope 隔离；同名文件或同内容事件不会跨 scope 自动合并。blob 可在同一 Worker 根内复用，
但引用与可见性仍属于具体 topic。SQLite 文件必须在本机磁盘，不能依赖网络共享盘实现 Worker 自治。

数据库驱动必须兼容仓库支持的 Node 基线与 Windows 安装，不以记忆功能为理由静默升级 Agent
或全局 Node。实现时锁定经 CI 验证的驱动版本；驱动选择不得改变这里的事务和接口合同。

## 7. 生命周期和准确的覆盖语义

### 7.1 入站摄入

Bridge 在现有准入与协作授权边界内记录实际收到的事件，按来源 ID 幂等追加。Hub 回传的授权材料
可以复制进该 Worker 的账本，带来源及可见性；不读取 Hub 的本地磁盘，也不以完整性为名抓取其他
Agent 的 provider sessions。记录观察到但没有运行的普通消息，不因此唤醒 Agent。

### 7.2 执行前准备

1. 建立本轮绑定：实例、topic、run、dispatch 和本地数据访问凭据。
2. 记录本次输入边界 `inputFence`；运行中后到的新消息归入后续准备，不能假装本轮已经读过。
3. 获取一个一致性快照：状态版本、已整理覆盖、未整理事件、纠正关系、Artifact 元数据。
4. 若积压适合放入近期原文窗口，直接组装；若无法覆盖，则先执行有界整理，或进入显式降级状态。
5. 返回本轮记忆包、工具入口和预算信息，再启动业务运行。

不在提示词里重复注入本轮用户消息、同一 dispatch 和近期账本中的相同事件。以来源 ID 去重，
保留原始用户要求的最高优先展示位置。

### 7.3 执行中 checkpoint

Agent 在重要决定、更正、验证或阶段完成时调用记忆工具，提交结构化变更及来源。
工具保存为候选，不允许模型指定其他 Worker 身份、任意数据库路径、越过 inputFence 的已读游标，
或通过新增记忆调用 handoff/complete 等协作动作。

本轮新产生的证据先形成 run 关联事件，再供 checkpoint 引用。来源可包含 inputFence 之前的已读事件，
以及本轮已落盘、与 runId 绑定的新证据；新证据不能把运行中到达但尚未读过的入站消息一起标成已处理。
尚未完成的动作只能标记计划或进行中。
候选包含 `baseRevision`、`runId`、`inputFence` 和来源 ID。校验后事务提交；冲突返回明确错误，
由 Agent 读取新版后调整，不能按最后写入者覆盖。

### 7.4 执行结束

先可靠保存实际结果和终止状态，关联合法候选，再按现有 Bridge 流程发送与协作收尾。
记忆分别记录工作结果、飞书交付、Hub 收尾三种实际状态，不把“已经写文件”当成“已经交付”。
新结果、缺失 checkpoint 或发送失败会产生待整理标记。业务已经成功而记忆更新失败时，不将业务
误记成失败；保留原文、失败原因和恢复队列。任务结束不要求每轮再做一次额外完整总结。

### 7.5 覆盖不是一个含糊的最后游标

分别记录：

- `observedThrough`：本地可靠保存到哪里。
- `stateThrough`：当前状态已处理的连续前缀；越过该前缀的本轮新证据另记覆盖集合，不能跨过缺口推进。
- `summaryCoverage`：历史摘要覆盖的范围及显式跳过的非语义事件。
- `inputFence`：某次运行最多实际接触到哪里。

一条消息可能已保存但未整理，也可能作为近期原文完整进入模型；不能因为存在一个摘要就把全部
账本标记为已压缩。每次组装都应能说明历史范围由哪些状态、摘要和原文承载，哪些尚未展开。

## 8. 长度预算和上下文组装

### 8.1 两种预算必须分开

Worker 能保证自己生成的记忆包、附件摘录及检索结果有界。一次 CLI 运行中原生系统提示、工具
schema、工具循环和 provider session 的持续增长，由宿主 runtime 控制。不能仅统计一段 memory
字符串就宣称整个 Agent 调用绝不超限。

每个 HostAdapter 应报告可知的模型上下文容量、输入大小、压缩/重置能力和 usage。无法观测的
部分使用保守预留并在诊断中明确；未知容量不按“无限”处理。Hermes 的原生上下文压缩继续由
Hermes 管理，任务记忆是独立的可恢复层。

总输入预算计算：模型容量减去输出预留、宿主固定开销、工具/多模态预留和安全余量，再分配给
本轮消息与记忆。所有渲染后文本与包装都计入。模型 tokenizer 可用时用实际 tokenizer；未知时
使用保守字节界和结构预留，不能用固定“4 字符等于 1 token”估算中文。

### 8.2 初始可调策略

以下是待实际工作负载验证的初始值，不是效果已验收的固定参数：

| 预算 | 初始上限 |
| --- | --- |
| 单次业务运行的记忆总预算 | 12,000 tokens，并受上述模型剩余容量限制 |
| 当前任务状态 | 3,000 tokens |
| 历史摘要 | 4,000 tokens |
| 近期原文 | 3,000 tokens |
| 本轮累计检索返回预留 | 2,000 tokens |

各部分可在总上限内借用空闲预算。检索预算是本轮累计量，不是每次调用都额外获得 2,000。
本轮长消息、图像和附件先消耗自己的输入预算，必要时缩小可选历史；完整附件以引用与按页摘录进入。

### 8.3 选择顺序

优先保留当前明确要求、有效关键约束、当前目标、相关未完成事项和最新纠正；然后保留近期原文；
再选择相关阶段摘要与证据目录。同一信息不在状态、摘要、近期原文三个位置重复铺开。
用于检索的摘要可以省略细节，正在执行所必需的固定数值和限制不能只留模糊转述。

每次记忆包附带版本、覆盖范围、剩余检索额度、历史缺口和未展开索引，不把这些内部元数据发给用户。

### 8.4 关键约束过多时的明确行为

任意长的必需约束与固定上下文上限不能同时无损满足。系统先合并等价条目、移出已失效约束、
回收可选历史预算，并按本轮目标取回相关原文。若同时必需的内容仍超出总输入容量，保持原记录，
将工作拆成有明确依赖的子阶段，或报告需要缩小本轮目标。不得截断约束后继续声称上下文完整。
显式 pinned 条目不能由预算器静默淘汰；新增 pinned 超限返回具体容量冲突，保留候选和原文。

## 9. 自动整理机制

### 9.1 触发器

- 每轮结果落盘后检查：未更新状态、重要目标/决定变化、交接/阶段完成、纠正事件。
- 执行前检查：积压无法放入近期窗口、记忆包接近预算上限。
- 空闲维护：处理已有待整理任务；没有新内容时不调用模型。
- 人工维护：重建某个范围、回滚错误记忆、检查完整性。

触发依据是新增内容大小、状态变化、来源覆盖和实际预算，不单靠聊天条数或定时每小时全文重读。

### 9.2 工作分解

`update-state` 将当前状态与新增事件整理成结构化变更；`summarize-range` 对结束片段生成叶摘要；
`condense-nodes` 对相邻摘要生成更高层节点；`rebuild-range` 在发现错误时从较低层来源重建。
它们属于同一个 Worker 的内部维护，不是 Hub dispatch，也不会真实 @ 任何 Bot。

先确定有界输入片段和输出预算，保存输入哈希与版本，再调用自己的模型。模型调用期间不持有数据库
写锁。提交时校验来源、覆盖、输出长度、版本和 fencing generation，再以事务发布。

模型输出过长可在有界次数内请求重新整理；输出为空、来源不存在、覆盖不连续或关键约束丢失时
拒绝发布。保留旧状态与待处理任务，不将 substr 截断后的文本伪装为有效语义摘要。

### 9.3 时机和资源

通常通过业务运行中的 checkpoint 更新状态，空闲时补充历史摘要。若 Worker 即将处理新任务，
优先业务准备和必要的小范围整理，暂停或延后不相关维护。每个实例设维护并发、每批输入、输出、
超时、调用次数和成本上限；上限耗尽形成可观察的积压，不无限循环烧 token。

原始输入足以在预算内覆盖尚未整理部分时，维护失败仍可正常工作；若关键状态陈旧且未整理部分无法
在预算内覆盖，应延后依赖这些历史的执行并说明原因。能独立完成的新请求可继续，但不能假装拥有
完整旧背景。失败不产生额外协作权限。

### 9.4 维护模型与工具能力

默认使用本 Worker 同一 Agent 配置；允许实例显式配置整理模型，但不强制增加独立 API Key。
HostAdapter 提供维护调用能力，优先无外部工具模式，输入只有指定记忆、来源片段和输出 schema。
维护结果作为数据处理，不走飞书输出、协作标记解析、Artifact 发布或业务任务完成流程。

不同 CLI 的无工具、结构化输出和模型选择能力必须实际探测。无法可靠执行独立维护调用的宿主，
应使用宿主原生 Hook/本轮记忆工具完成同一合同，或明确报告尚未通过支持验收；不能靠“装了 Skill”
就宣布具备全自动维护。相同 Windows 用户的文件权限不等于强隔离，不能声称提示词可阻止全部越权。

## 10. 检索与展开

基础版本无需外部向量服务。先实现精确 ID、日期/范围、状态类型、关键词和中文可用的全文检索。
索引写入时生成中文短词/字组与英文标识词，配合全文排序；必须用中文短词、数字、错误码和路径
样例验收，不能只依赖默认英文分词。语义检索以后可以作为同一 Worker 的可选增强，不影响完整账本。

读取分三步：

1. `search` 返回有界候选卡片：来源 ID、时间、类型、简短片段、相关更正。
2. `inspect` 返回候选附近的事件或摘要结构，说明哪些细节可展开。
3. `expand/read` 按 ID、范围或子节点取回原文，支持分页，消耗本轮累计预算。

所有工具默认绑定当前 topic，不靠模型自己记得加过滤条件。跨话题读取只能是另行授权的显式操作。
低相关或缺少依据时返回“未找到”和可用范围，不编造答案。全文扫描、检索结果和工具序列化都必须
有界；扩大检索范围不等于把所有内容一次输出。

文件引用同时区分 locator、sha256、当时本地路径和当前是否 materialized。读取旧路径前验证，
不能把另一台机器的绝对路径当成可用文件。记忆只引用现有 Artifact 传输能力，不暗中实现一套跨机下载。

## 11. 通用运行接口和工具合同

本地记忆运行层提供以下宿主接口，不暴露中央共享服务：

```ts
interface WorkerMemoryRuntime {
  ingest(binding: WorkerBinding, events: ObservedEvent[]): Promise<IngestResult>;
  prepare(binding: RunBinding, budget: ContextBudget): Promise<PreparedMemory>;
  checkpoint(binding: RunBinding, change: MemoryChange): Promise<CheckpointResult>;
  query(binding: RunBinding, request: MemoryQuery): Promise<BoundedMemoryResult>;
  finalize(binding: RunBinding, result: ObservedRunResult): Promise<void>;
  maintain(binding: WorkerBinding, limits: MaintenanceLimits): Promise<MaintenanceResult>;
}
```

上面是提案类型，不是现有 API。CLI 使用同一实现，供只能执行命令的 Agent 使用：

```text
lark-channel-bridge memory status
lark-channel-bridge memory read
lark-channel-bridge memory search --query "约束变更"
lark-channel-bridge memory inspect --id <id>
lark-channel-bridge memory expand --id <id>
lark-channel-bridge memory checkpoint --file <candidate.json>
```

正常运行不要求模型传入 agentId、topic 路径或数据库位置。Bridge 通过本轮环境和本地绑定文件
注入这些信息；当前 `local-context read/search --scope` 保持兼容，转发到对应账本只读视图。
未绑定运行的运维命令可以显式选择实例与话题；这属于本机运维能力，不从自然语言中猜测权限。

checkpoint 返回 `accepted / no_change / stale_revision / invalid_sources / over_budget` 等明确状态，
包含新版本或修正所需信息。工具成功写入才算记忆已保存，模型在最终答复中说“记住了”不算证据。

本轮累计检索额度由存储层按 run 记录，跨多个 CLI 子进程调用也不能重置。超出预算返回分页句柄
和剩余额度；需要重新分配时由 prepare 生成新包，而不是让模型自行绕过上限。

## 12. 各 Agent 的接入与 Skill

业务语义相同，宿主工程分别实现，不硬编码 World、Justice 等角色：

| 宿主 | 加载/运行接入 | 工具/规则接入 | 专项验收 |
| --- | --- | --- | --- |
| Codex | Node bridge prepare/finalize；保持群聊 fresh session | 当前 profile 的 Skill/运行约定与 CLI | 新 session 连续性、环境清洗后的绑定 |
| Claude Code | 同一 bridge 生命周期，支持宿主 Hook 辅助 | 对应安装目录的 Skill/指令 | headless 工具调用与 Hook 不重复写入 |
| Antigravity | bridge 自动注入记忆；适配 agy 实际能力 | 支持的 Skill/指令/命令入口 | 最终批量输出、真实 headless 模式 |
| DeepSeek Harness | 独立 adapter 的准备与收尾 | 当前 headless profile 可访问的工具/Skill | CLI 入口、profile、结果与维护调用 |
| Hermes | 可撤销 Hook/provider 适配，不重装或覆盖原记忆 | Hermes 原生目录与 Hook 能力 | 原生全局记忆不冒充话题状态、不重复注入 |

每种宿主可以有自己的 SKILL.md、安装文档和生命周期脚本，允许必要冗余。安装清单记录本项目拥有
哪些文件及版本，更新/卸载只处理这些文件。不能全局覆盖用户 AGENTS.md、SOUL.md、原生记忆或登录。

Skill 要教会 Agent：读取当前状态、对冲突查原文、区分事实和推测、按 ID 更新、阶段完成时 checkpoint、
超限时整理、保存失败时重试。强制加载和维护触发由运行层承担；模型不必知道自己的业务昵称。

新宿主通过能力描述、绑定目录、工具入口、整理调用、安装卸载和合同测试接入。仅完成检索或安装
不等于通过完整记忆支持验收，状态必须写明。

配置以实例为单位继承可选默认值；同一机器上的两份同类 adapter 可以分别覆盖。拟议最小配置如下，
字段只有实现后才是有效部署参数：

```json
{
  "memory": {
    "enabled": true,
    "maxMemoryTokens": 12000,
    "maintenance": {
      "backgroundEnabled": true,
      "useAgentModel": true
    }
  }
}
```

状态根和实例身份默认由当前 profile 推导并持久化，不要求用户配置数据库、索引或摘要树。
完整验收后，新安装启用该能力；存量安装先完成可回退迁移和归属检查。模型选择等高级项按需提供，
不把新密钥或统一安装路径变成正常使用前提。

## 13. 一致性、中断与恢复

- 每 topic 的短写事务串行；SQLite 唯一约束负责幂等，不能只靠进程内 Set。
- 多进程操作使用本机 topic lease 与 fencing；进程退出或超时后旧维护任务不能发布。
- 业务和维护任务都提交 baseRevision；候选过期时重读重算，原文摄入不因冲突回滚。
- 不在模型调用期间持有长事务或文件锁。摘要候选只有来源关系和状态一起提交成功才可被提示词选中。
- blob 先写临时文件并校验后落盘，再提交引用；崩溃遗留的孤儿 blob 可以后续清理，不产生坏引用。
- 重启恢复 pending/running 的维护任务，校验输入哈希与版本；过期任务重新准备，不盲目接续旧输出。
- 维护结果幂等发布；同一范围重试不重复制造摘要或重复推进覆盖。
- 回滚派生记忆会建立新 revision，并重新检查其后事件；不回滚原始事实，也不回滚 Hub 的负责人。
- 备份使用一致性 SQLite snapshot 和 blob 清单，不直接复制活跃 WAL 文件集合冒充有效备份。

记忆中的外部内容保留来源与信任类型。历史消息中的命令属于历史内容，不升级为系统指令。
Hub 当前授权优先于旧记忆中的身份或权限叙述。数据导出、遗忘和清理单独提供明确运维入口，不
把“记忆永远保留”解释成不能删除；删除授权源时重建相关派生节点。

## 14. 存量迁移、兼容与回退

当前共享 JSONL 不删除、不覆盖。迁移生成新数据库并保存来源文件指纹、来源行与归属依据。

能确定接收 Worker/作者/话题的记录复制进相应实例；同一消息复制 N 份允许。现有 bot-result
记录可能缺少作者，不能按目录猜成某个 Agent 的亲历结果。无法可靠确定的内容保留在只读 legacy
档案并标记归属未知，只有经显式可见范围确认后才作为参考材料导入，不伪造“自己已完成”。

先读取原目录生成一个带文件边界的快照，再逐步摄入快照后的追加，避免迁移中运行 Bot 导致漏记。
按来源指纹与行/事件 ID 幂等，重复执行迁移安全。SQLite schema migration 使用版本与备份。

Pilot 保持 schema-v1、缺省 role 和单机 all 兼容；记忆配置是可选新增项。worker 模式只配置自己的
状态根和现有 Hub 地址，不能为了记忆维护启动 Hub。禁用新记忆时恢复现有 local-context 入口，
保留新数据库、旧账本、登录和 Artifact；回退不依赖删除任何运行状态。

## 15. 观测和人工检查

本地 status/doctor 展示：记忆版本、账本范围、摘要覆盖、待整理大小、最近整理时间、输入/检索 token、
维护调用与成本、失败与重试、历史缺口、降级原因。诊断默认不输出正文或凭据。

每次运行保留无正文或最小正文的 projection manifest：具体采用了哪些状态项/摘要/原文 ID、
各自预算、哪些内容未展开、对应当前模型容量与观测能力。这样可以区分“原文没收到”“收到了但未
整理”“摘要遗漏”“检索未命中”和“模型看到了仍答错”。

正常维护不在飞书刷屏。只有业务无法继续、历史缺口直接影响任务或需要用户明确取舍时才报告。
人工可按 ID 查看来源、标错、重新整理、恢复版本和导出完整 topic。

## 16. 代码落点和实施顺序

建议新增 `src/memory/`：scope、store、events、state、summaries、projection、budget、retrieval、
maintenance、migration、host-contract。`src/cli/commands/memory.ts` 暴露工具；原 local-context
调用新只读接口。Node channel/run-flow 负责 prepare/checkpoint/finalize；Hermes Hook 通过本地
CLI 或等价适配调用，避免另写一套摘要/预算算法。

Pilot 只增加独立实例根、宿主安装资产和后台维护启动选项，不承载摘要语义。Hub 状态机和 API
保持不变。英文/中文设计、Agent 接入、运维和能力状态须随实现更新；当前旧路线图关于提示投影
的部分描述与代码有差异，实现时应以实际代码核对并收敛，不能据旧文档认定已有摘要能力。

工程顺序如下，属于同一完整交付，不把尚无自动整理的半套系统宣布为完成：

1. 定义合同与话题资料集；实现持久账本、scope、幂等、迁移和查询。
2. 实现结构化状态、来源校验、revision、checkpoint 和恢复。
3. 实现历史摘要来源树、预算组装、展开和累计检索预算。
4. 实现维护队列、模型调用适配、失败重试和前台/后台协调。
5. 接入全部维护中的 Agent 宿主、实例安装卸载、配置与运维。
6. 完成故障测试、真实宿主和独立 Worker 机器验收；最后再按证据启用默认配置。

不按工作天数预估 AI 编码成本。完成判断依据下列合同与效果验收。

## 17. 验收标准

### 17.1 确定性合同测试

| 场景 | 必须结果 |
| --- | --- |
| 两个同类 Bot、同一 cwd、同名话题 | 各自实例和 topic 正确绑定，不靠昵称猜身份 |
| 多话题交错、迟到和重复消息 | 不串话题、不重复摄入；保留来源时间和纠正关系 |
| 摘要与状态提交时 kill 进程 | 原文完整；无半成品摘要、游标跳跃或坏引用 |
| 旧维护与新 checkpoint 竞争 | 旧 revision/fence 无法覆盖新状态 |
| 模型空输出、超长、假来源 | 拒绝发布、保留积压，不以截断冒充成功 |
| 中文、数字、路径、超长工具结果 | 组装及检索预算成立，精确原文可按 ID 读取 |
| 多个 CLI 子进程连续检索 | 共享本轮累计额度，不能通过重开命令绕过 |
| 状态恢复与 legacy 迁移重复执行 | 幂等、可回退，不修改旧账本和用户登录 |
| Hub 停止或机器无本地 Hub | 本地 read/search/checkpoint/maintain 不依赖中央目录 |
| 记忆或摘要中出现协作控制标记 | 不创建 dispatch、不发飞书、不完成业务任务 |

### 17.2 真实模型效果测试

建立版本化的中文长话题资料，不只用 mock 摘要器。至少包含：

- 在很早处给出限制，中途被引用，后来明确改变；正确使用最新要求并能解释来源。
- 多个 Agent 给出相互矛盾结论；保留争议，不将多数报告当成用户决定。
- 几百轮中的精确数值、路径、提交和附件；从摘要展开到准确原文。
- 大量已完成事项与少量长期未完成事项；下一轮继续正确工作。
- 两个高度相似话题；不借用另一个话题的决定。
- 大文件与超长消息；保留引用并按需读取，不能靠压缩隐藏当前必要条件。
- 有效关键约束超过容量；触发明确处理路径，不静默丢失。
- 第一次压缩有错误；可标错、追溯和重建，不让错摘要逐层固化。

硬性约束类用例要求所有指定关键条件满足；来源回查要求返回正确事件/Artifact ID。其他开放问答
使用人工可复核答案、原文依据和任务实际完成结果，不只依赖另一个模型给分。记录各模型多次运行
结果及失败样例，不用单次演示宣称绝不遗忘。

### 17.3 规模、成本和部署验收

用超过模型窗口多倍的 topic 以及多 topic 数据集验证：记忆注入不随总历史线性增长，检索有界，
每轮不全表读取整机历史。测试 1 万与 10 万条记录级别的本地账本，报告实际延迟、内存与磁盘，
不先编造未经测量的毫秒承诺。记录归纳额外调用与 token，并验证无新记录时零整理调用。

每个声称支持的宿主分别验证 headless 加载、更新、检索、整理、重启、失败恢复和卸载。至少一次
真实独立 Worker 验收：机器上没有 Hub 进程或中心账本副本，连接远端 Hub 正常协作，本地记忆可以
继续维护；与 Hub 共置的 Worker 使用相同安装资产和接口。自动化隔离环境只能作为合同验证，不能
替代第二台机器和飞书真实事件验收。

仓库实现阶段运行相关授权、可见性、幂等、Pilot 和文档测试，以及 `pnpm test`、`pnpm typecheck`、
`pnpm build`、`git diff --check`；Pilot 变更额外解析脚本并安全运行配置预检。
