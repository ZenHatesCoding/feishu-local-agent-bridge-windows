## 一、这个方案到底想干什么

先剥掉包装看本质。这个项目已经有一个能跑的多 Agent 协作系统：飞书群做消息面、
Hub 做控制面、各电脑的 bridge 做执行面，跨机协作已实现并通过第二台真机验收。
**LAN 方案不是要重做协作内核，而是要换掉"通道"**：把消息面从飞书（SaaS，
消息/文件/任务数据都在飞书云端）换成自建的内网 Web 工作台，让协作数据留在
局域网内；模型访问仍走各 Agent 自己的外网连接。

所以方案的真实交付物是三层：

| 层 | 内容 | 现状 |
| --- | --- | --- |
| 重构层 | 把协作内核和执行流程从飞书入口中抽出，变成通道中立 | 现有代码的飞书耦合集中在少数几个点（见下节） |
| 服务层 | 新的中心：用户认证、会话/事件存储（SQLite）、文件服务、claim/租约调度 | 现有 server.ts 只有 Agent 面 API，全部要新建 |
| 产品层 | 浏览器工作台：三栏布局、结构化 @、任务面板、流式进度、断线恢复 | 完全没有，是最大的新建工程 |

方案最核心的两个决策：

1. **组合架构**：专用协作前端 + 自建会话服务 + 复用 Hub 内核 + 复用执行桥；
   Zulip/Mattermost/Matrix 只当设计参考和可选通道，不当底座。
2. **独立部署**：新系统与现有飞书系统完全隔离（新身份、配置、端口、数据目录），
   不迁移数据，Hermes 不纳入。

## 二、代码事实核查：方案的复用声称是否属实

我逐文件读了 `src/collab`（80KB/15 文件）、`src/agent`（80KB/14 文件）和
`src/bot/channel.ts` 等通道面代码（~250KB），并用 `pnpm test` 跑了基线：
**113 个测试文件、636 个测试全部通过**。结论：方案的复用表基本诚实，且偏保守。

| 方案声称 | 代码验证结果 | 复用度 |
| --- | --- | --- |
| `hub.ts` 状态机可复用 | 属实。604 行内存状态机 + JSONL 重放，逻辑上只有 3 个飞书触点（`openId` 注册、`listChatAgentIdentities(chatId)`、feishu locator 校验） | 高 |
| 协议语义（双钥匙/可见性/幂等/因果深度） | 属实且质量高。可见性过滤在 Hub 端强制执行；`ask` 收尾、标记修复（Hub 授权单次重做）、causal depth 上限都有测试 | 高 |
| `server.ts/client.ts` 可演进为 LAN API | 属实。已是 HTTP + Bearer + 幂等提交 + 每 Agent 独立凭据；缺 claim/heartbeat/fencing——这本来就是分布式路线图的 P1 | 高 |
| `bridge-adapter.ts` 需要通道中立化 | 属实。耦合点：`NormalizedMessage`（飞书类型）、mention 解析、coordinator 模式直接用 Lark channel | 中 |
| `context.ts` 上下文投影 | **飞书味最重**：prompt 契约里全是 lark-cli 命令、飞书消息引用、`collab-artifact.cmd --reply-in-thread`。LAN 通道需要整体重写规则文本，但信封结构（contract/rules/localJournal）可保留 | 低（文本）/ 高（结构） |
| Agent 适配器可复用 | 属实。`AgentAdapter` 接口本身通道中立，只有 `AgentBotIdentity.openId` 和 `lark-channel-env` 两个注入点 | 高 |
| 运行流程需从飞书入口抽出 | 属实。intake→runAgentBatch→processAgentStream→回复 的管线埋在 69KB 的 `channel.ts` 里，这是重构的最大单体 | 中 |
| 存储需迁 SQLite | 属实。现为单写者 JSONL + 撕裂容忍（一次提交=一行=一个事务），迁移 SQLite 是路线图 P2 本来就要做的 | 顺势 |

**一个方案没写但很重要的量化**：真正"通道中立化"的工程集中在三处——
`TaskAddress{tenantKey,chatId,threadId}` 换成 `deploymentId+conversationId`、
`context.ts` 的 prompt 契约重写、`channel.ts` 运行管线抽取。协作内核的语义和
测试资产（636 个测试是安全网）可以基本原样搬过去。这验证了方案"自研集中在
会话体验、通道接入和可靠调度"的自我定位是准确的。

## 三、业界坐标系

> 调研方法说明：三个独立调研线程（多 Agent 编排框架/协议、自托管 AI 工作台产品、
> 聊天平台做 Agent 骨架），检索约 20 轮/线程。受限说明：调研环境无法逐页打开
> 网页验证，结论基于搜索摘要与项目文档描述，个别新兴项目（已标注）成熟度未验证。

### 3.1 现有产品覆盖了多少

**核心结论：方案要做的组合（结构化 @ + handoff/ask 语义 + 多电脑执行节点星型
拓扑 + 事件溯源会话层 + 话题内文件权限）在现有开源产品中没有单一对应物。**
各产品恰好各覆盖一角：

| 类别 | 代表 | 与方案的差距 |
| --- | --- | --- |
| 多模型聊天 UI | LibreChat、Open WebUI、LobeChat、AnythingLLM | 全是"API 聚合器"架构：Agent=带系统提示的模型调用配置，无长驻进程身份、无 Agent 间消息、无任务所有权。接 CLI Agent 要靠 claude-code-proxy 一类兼容桥，等于把编码 Agent 降格为无身份端点 |
| 工作流平台 | Dify、n8n、Flowise | 设计时预定义 DAG，人是"预定义插点"，Agent 不能在运行中自主 @ 另一个 Agent。Flowise 的 Supervisor 模式交接语义最强，但仍跑在预定义 flow 里 |
| Claude Code 编排工具 | claude-squad、Crystal、opcode、Conductor、AgentsRoom | 主流是单机 tmux/worktrees 并行会话管理。Conductor 是 Mac 闭源且新方向是云端 SaaS；AgentsRoom 有 Teams 链式交接但是商业闭源 |
| 最接近的开源项目 | [agent-room (agent-room-alkl)](https://github.com/agent-room-alkl/agent-room)、[ai-maestro](https://github.com/23blocks-OS/ai-maestro)、[agentdeck](https://github.com/AliceLJY/agentdeck) | agent-room（深挖结论：**不能作底座，只宜借鉴**）：多运行时（含 Antigravity）+ MCP-native + 自托管，但协议 v0.1/服务端 v0.5-rc 的快速变形期；GitHub 仓库是内部仓库的自动同步镜像（社区无法治理）；协作语义绑定同一 repo 的 PR/代码审查；license 未知、多机机制未知、任务所有权/授权语义无证据。ai-maestro：唯一明确"跨电脑移动 Agent"+A2A 消息，但是 Rails 的管理/技能平台而非话题协作室。agentdeck：多 CLI Web 终端 + tmux 断线恢复 + Tailscale，功能面高度重合但单机单 deck、无 Agent 间语义 |

**"多台电脑上的 Agent 汇聚到一个自托管中心"这个星型拓扑，没有主流产品实现过**；
普遍假设单机或云端 SaaS。方案自建会话/事件/授权层所瞄准的空白是真实存在的。

**技术栈对照**：SQLite 默认 + 需要时升 Postgres 是 Open WebUI/Flowise/n8n 的共同
路径，与方案选型一致；Socket.IO（聊天 UI 事实标准）与 SSE（模型流式）都与
方案的 Node.js 事件流同构；文件共享方面没有任何产品有"话题内 Artifact + 权限"
的中间层（聊天 UI 是对象存储+RAG，Agent 工具是 git worktrees+本地文件）——
方案的 Artifact 设计在这个坐标系里是独有的。

### 3.2 编排框架与协议

**核心结论：方案自建的东西，没有一样是"业界已有标准件而被无视"；2025 年的主流
实践恰恰是"自建轻量持久编排层 + 复用 CLI 运行时的执行循环"。** 但有几个标准
值得借概念、对齐命名。

**框架坐标系**（LangGraph / CrewAI / AutoGen(AG2) / OpenAI Agents SDK /
Claude Agent SDK）：

- 这些框架的"Agent"基本都是**进程内函数/对象 + LLM**，不是"另一台电脑上的独立
  CLI 进程"；部署形态偏单机库或云 API。唯一原生分布式的是 AutoGen 0.4 的 actor
  runtime，但编排语义是对话式 group chat（LLM 选发言者），不是"人监督下的授权
  与交接"。
- **没有任何框架自带"人类监督多 Agent 交接"的持久化 Web UI**：LangGraph Studio
  最接近（HITL 中断+检查点恢复）但定位是调试台；AutoGen Studio 是构建器；
  OpenAI/CrewAI 的 UI 在云产品侧。
- 跨 Agent 的任务所有权状态机（claim/handoff/ask 路由、授权）**没有任何框架
  内置，普遍留给应用层**——Claude Code 官方 Agent Teams 用 markdown 任务文件
  自建 assign/claim，Vibe Kanban 用看板列自建状态机，AWS 甚至专门撰文论证
  "agents need an inbox, not another chat window"。本项目 Hub 的语义深度
  （双钥匙+可见性+因果链+幂等）超过上述所有产品层实现。
- 业界分层趋势印证方案思路：LLM 执行层与确定性编排/持久层正在分离（Temporal
  × OpenAI Agents SDK 官方集成做 durable agents、LangGraph 强调确定性控制流）。
  方案"Hub 是确定性协调代码不是 LLM"与行业方向一致。

**协议层判定**：

| 协议 | 判定 | 对方案的动作 |
| --- | --- | --- |
| A2A（已入 Linux Foundation/AAIF，v1.0 于 2026-03 发布） | 跨组织互操作协议，不是本场景方案：假设 Agent 是常驻 HTTP/gRPC 端点（CLI 运行时不是）、不定义工作区/文件共享语义、没有授权/咨询语义；社区实测公网宣称支持的端点近零真实合规 | 不押注（方案没押注，正确）；但 Task 状态机命名（submitted/working/input-required/completed/failed/canceled）和 Agent Card（能力发现 JSON）值得对齐命名，为未来对外互通留口——分布式路线图已引用 A2A，方向一致 |
| MCP（Anthropic，已捐 AAIF） | "工具接入而非 Agent 间协作"的理解与官方口径一致；有人拿 MCP client 做多 Agent 消息传递（mcp-agent 等），但 tools/call 是无状态 RPC，没有所有权/生命周期语义 | Agent 接工具时用标准件；Agent 间总线不走 MCP（方案正是这么定位的） |
| AG-UI（CopilotKit 主导，1.0） | "Agent 后端→前端 UI"的标准事件流协议（RUN_STARTED、TEXT_MESSAGE_CONTENT、TOOL_CALL_* 等约 16 种事件类型），LangChain/Microsoft/AG2/Bedrock 均有集成；与工作台"消费多 Agent 事件"的需求同构 | **方案未提及，建议纳入**：工作台前端事件协议对齐 AG-UI 类型学（或直接复用），表示层少造一轮轮子；它不解决授权/持久化，与 Hub 无冲突 |

**产品形态补充**（框架调研线程的独立发现，与 3.1 交叉印证）："一个界面管多个
编码 CLI Agent"是 2025 下半年的真实热门品类——Vibe Kanban（多运行时+自托管
看板但单机）、devteam（Claude/Codex/Gemini 但本地 TUI）、CCCC（本地优先协作
内核+聊天通道）、WuKong/Claude-Collab 等——**几乎全部单机；真正的多机只有
云端方向（Terragon，且已归档）**。"局域网多机 + 自托管中心 + 人类监督"这个
位置在开源界无人占据，是方案的真实差异化。风险提示：CLI 运行时的 headless/
流式接口仍在快速变化（Claude Code agent-teams 功能高频迭代），方案"每个运行时
一个适配器"的隔离策略是对的抗法。

### 3.3 聊天平台做底座

**核心结论：所有"多 Agent 在聊天平台上协作"的已知先例（mattermost-plugin-agents、
talon、OpenClaw 生态、matrix-agents 等 2025 年起密集出现的项目）最终形态都是
"聊天平台只当人机界面/通道，协作骨架（任务状态、所有权、编排）永远是自建代码"。
没有发现任何项目成功把整包聊天平台本身当协作骨架**——因为任务所有权、dispatch、
ledger、上下文可见性、artifact 引用不在任何聊天平台的数据模型里。这把方案第四节
"不整包部署"的决策从"架构论证"升级成了"实证结论"。

平台逐个对照（数据来自官方文档与社区来源，个别资源数字建议引用前复核）：

| 平台 | 关键事实 | 对方案的意义 |
| --- | --- | --- |
| Zulip | 唯一整包仍纯 Apache-2.0；但 Python/Django 多服务体系最低 ~2GB 内存；Bot 是一等用户；事件推送是**拉模型**（注册事件队列→游标→长轮询，Agent 无需入站端口） | 不当底座；其"服务端事件队列+游标+断线续读"是自建会话层最值得复刻的机制 |
| Mattermost | 单 Go 二进制最轻（~1-2GB 可跑）；但核心目录自 2024 年起改为 source-available 许可（非纯 MIT），条款由商业公司主导且已变更过 | 方案对 Mattermost 许可的谨慎（"不能整库当 MIT"）被证实是对的；可作可选通道 |
| Matrix/Synapse | 事件模型（不可变事件 ID=内容哈希、sync 游标）设计优秀；但 Synapse GB 级内存、轻量实现谱系连续动荡（Conduit 停维、Conduwuity 停开发）、联邦/E2EE 对内网 Bot 是纯负担 | 只借鉴事件模型设计；现有 hub 的"追加式账本+序号+幂等键"已经与 Matrix 事件模型同构 |
| Rocket.Chat | Meteor+MongoDB 最重；MIT 基础上附加非竞争条款；生态重心在客服 | 排除合理 |

**技术选型的实证校准**（对方案第六、七节的具体修正建议）：

1. **实时通道**：Socket.IO 仍活跃维护但非必需——单实例场景用原生 `ws` + 简单
   重连更优（避免私有协议两端锁定）；单向推送场景 SSE 是行业回潮的主流共识。
   方案把 Socket.IO 列为"可选"是对的，可以更进一步：默认不用。
2. **文件上传**：tus 协议成熟但适用边界是"大文件+不可靠网络"；内网 KB/MB 级
   artifact 用 HTTP PUT + 内容哈希即可幂等。方案"大文件需要时再接 tus"的分期
   被验证为正确。
3. **SQLite 边界**：WAL + busy_timeout + **本地盘**是硬约束——官方明确 WAL 的
   共享内存/锁语义在 NFS/SMB 上不成立，真实世界有损坏案例（opencode、OpenClaw
   都踩过）。方案"不把 SQLite 置于共享网络盘"写对了；追加式事件日志的单写者
   串行恰好是 SQLite 的理想属性。规模边界：每秒百级事件远未到瓶颈，迁
   PostgreSQL 的触发条件应该是"需要多节点/HA"而不是数据量。
4. **内网 HTTPS**：自建内部 CA 对"个人局域网+异构设备"是持续负担；更优解是
   Tailscale HTTPS（`tailscale cert` 为 MagicDNS 机器名自动签发真证书）或自有
   域名 DNS-01 ACME——与本项目现有 Tailscale 网络层零成本衔接。方案说"内部
   CA 或可信证书由部署提供"，此处可以更具体地推荐 Tailscale cert 路线。
5. **Git 服务**：Forgejo（社区治理）与 Gitea（生态/迭代）同源同型皆可，内网
   自用看重长期可控选 Forgejo。方案已列 Forgejo，无异议。

## 四、如果我自己做，我会怎么做

### 相同的部分（而且是重要判断）

我自己设计的话，宏观架构会和这个方案高度一致，因为有几个判断我认为它做对了：

1. **确定性 Hub 而不是 LLM 编排器**。LangGraph/CrewAI/AutoGen 一类框架把编排
   逻辑放进图或 LLM 循环，适合 API 型小 Agent 流水线；本项目要协调的是四个全功能
   编码 Agent，确定性状态机 + 双钥匙 + 可见性过滤才是防唤醒风暴和上下文污染的正解。
   这是全项目最值钱的资产，方案完整保留它，正确。
2. **星型拓扑 + 单进程中心 + SQLite**。所有 Worker 主动外连、不开入站端口，中心
   单实例单数据库、一个事务边界覆盖消息+dispatch+outbox。这个规模下任何更复杂的
   拓扑都是过度设计，方案明确拒绝了多 Hub，正确。
3. **不整包部署 Zulip/Mattermost**。任务面板是 Hub 状态的投影、结构化 @ 必须服务端
   验证、所有权状态机是核心 UX——这些没有一个是通用聊天平台给的。加上本项目是
   Windows-first 运维而主流聊天服务器都是 Linux/Docker-first，整包部署的适配成本
   会吃掉省下的前端成本。
4. **范围裁剪**：桌面优先、不做手机/视频/审批/在线编辑、模型走外网不搞离线推理、
   文件先用中心磁盘不做分布式存储。每一刀都合理。

### 不同的部分

v1 按重要性列出六条分歧；v2 依据所有者反馈撤销前三条（标注于各条内），保留
后三条与三条增量建议：

**分歧 1：~~验证顺序——先补飞书真机验收~~（v2 已失效：验收早已通过）。**
v1 依据本机路线图"第二台真机待验收"的字样提出先补验收；所有者确认验收已在
另一台电脑上完成，路线图状态已刷新为"已通过"。此分歧撤销。

**分歧 2：~~工作台价值假设先做只读观察页廉价验证~~（v2 已撤回：AI 执行前提下
不成立）。**
v1 建议用 10-20% 成本的观察页提前验证产品假设，这是人类工程经济学。AI 执行下
直接建完整工作台：验收靠自动化端到端测试 + 所有者真实使用；体验不对就重做，
重做成本可接受。方案已改为"契约先行、并行轨道"结构，工作台是独立轨道之一。

**分歧 3：~~v1 中心砍到轮询+单管理员~~（v2 已撤回：AI 执行前提下不成立）。**
v1 建议推送降级为轮询、多用户延后，同样是人类投入风险控制。AI 执行下直接建
目标形态（SSE/outbox/心跳一次到位），claim/幂等/fencing 的正确性不变量不变。
范围边界（哪些能力进首版）仍由方案第九节的范围裁剪决定，与分期无关。

**分歧 4：把"运行进度流"提升为一级交付物。**
方案提到"进度在同一个运行块中更新"，但 worker→center→浏览器的流式事件通道
是工作台体验里性能最敏感、工程量最容易被低估的部分（现有飞书通道的保活心跳
机制不能直接搬）。我会在实施分解里给它独立的位置和验收标准，而不是混在
"接入 Worker 领取与恢复流程"里。

**分歧 5：两通道维护税要显性化并设决策点。**
方案承诺"保留现有飞书入口的行为"，意味着从此每个协议改动都要过两个通道的
契约测试。这是永久成本。我会明确写上：LAN 系统达到某个验收里程碑（比如完整
闭环跑通 + 工作台日活稳定）之后，重新评估飞书通道是继续维护、冻结还是退役，
而不是默认无限期双轨。

**分歧 6：主权收益的措辞要更诚实。**
方案说"局域网限定协作链路"，这是对的，但容易让人以为"数据不出内网"。实际是：
协作数据（消息、文件、任务状态）留内网，但每次模型调用仍然把任务内容发到
外网模型服务商。这是通道主权，不是内容主权。我会在方案里加一句预期管理，
避免未来使用者拿"内网部署"当保密承诺。

**补充 1（调研带来的增量，非分歧）：工作台前端事件协议对齐 AG-UI。**
调研发现 AG-UI（CopilotKit 主导，LangChain/Microsoft/AG2/Bedrock 均已集成）
已经把"Agent 运行时→前端"的事件类型学标准化（RUN_STARTED、
TEXT_MESSAGE_CONTENT、TOOL_CALL_* 等约 16 种事件）。方案没提这个标准。我会在
worker→center→浏览器的事件流设计中对齐 AG-UI 的事件命名（或直接复用其 SDK），
表示层少造一轮轮子——它不碰授权/持久化，与 Hub 内核零冲突。

**补充 2（调研带来的增量，非分歧）：任务状态命名向 A2A TaskState 对齐。**
A2A 的 Task 状态机（submitted/working/input-required/completed/failed/
canceled/rejected）与方案的任务生命周期高度同构。不押注协议本身（其真实合规度
还很低），但把内部状态命名对齐它，未来对外互通时适配成本最低。

**补充 3（竞品启发，非分歧）：评估"会话走自建事件层、工具/文件走 MCP"的混合
接入。** agent-room 选择 MCP-native 的原因值得注意：所有主流编码 CLI 都内置
MCP 客户端，用 MCP 做 Agent 接入层比包装私有协议便宜。方案的 Agent 统一工具
入口（查询授权上下文、读文件、发成果）可以考虑直接做成 MCP server——CLI 侧
零适配成本，而消息/授权/dispatch 仍走自建事件协议。这不改变 Hub 内核，只是
给 Agent 工具入口多一个标准化的外壳。

### 实施结构（v3：方案已按 AI 执行 + 验证阶梯重写）

方案原"五步顺序"已重写为"契约先行 + 四条并行轨道 + 验证阶梯"（见方案
"开发方式""验证阶梯""实施轨道"三节）：轨道 1（契约与抽取，含单机仿真骨架）
先行解阻，中心/Worker/工作台三轨道并行，集成与运维收尾。阶段按验证环境切：
L0 单机仿真覆盖全部协议与产品验收，L1 沙箱演练覆盖环境差异，L2 真机日只跑
预置清单——把没有局域网环境的当前阶段能做的开发和验证全部做完。

v1 评审建议的最终去向：被方案吸收的——AG-UI 事件类型学对齐、A2A TaskState
命名对齐、MCP 作 Agent 工具接入层评估、原生 WebSocket 替代 Socket.IO、
Tailscale 证书路线；被新前提撤销的——只读观察页分期、薄 v1 分期、先补真机
验收（已完成）。

## 六、最终判断（v3）

**方向正确，架构合理，文档诚实度高，市场空位真实，分布式基线已验收。** 复用
评估与代码事实相符（第二节）；三线调研交叉印证：现有产品最多同时满足"多运行
时、多电脑、人类监督工作台"三者中的两个，"局域网多机 + 确定性 Hub + 人类
监督"的组合在开源界无人占据；方案自建的部分都是业界同样在自建的部分，该借的
标准（A2A 命名、AG-UI 事件、Zulip 事件队列、Matrix 游标）都可以低成本借到。

**按"AI 执行 + 验证阶梯"重写后，方案在当前无局域网环境的条件下即可开工。**
"契约先行 + 并行轨道 + 验收即测试"与"代码不是瓶颈、大不了重来"的执行哲学
自洽；"按验证环境切阶段"回答了"没有局域网怎么办"——单机仿真骨架覆盖全部
协议与产品验收场景，沙箱演练覆盖环境差异，真机日只剩证书/主机名/自启动/物理
断网等环境专属项，按运行手册执行。飞书分布式 P0"本机集成测试先行、真机一次
通过"的先例证明这套打法有效。

**仍然成立的两条提醒**：双通道维护在 LAN 闭环验收后需要一个显式的
"维护/冻结/退役"决策点；"内网部署"是通道主权不是内容主权，方案的预期管理
要写明。其余小缺口（凭据轮换、运行指标、worker 服务包装、浏览器并发语义）
在对应轨道内补齐即可。
