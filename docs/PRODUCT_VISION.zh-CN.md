本文档定义这个项目最终要交付给用户的体验。架构、协议和代码可以演进，但不能以牺牲
这里的体验为代价。出现实现分歧时，以本文档为准。

## 一句话目标

用户只需要在飞书里像带一个小型团队一样工作：一个飞书话题就是一段对话，人和 Agent
都可在其中自然互回；只有转交或咨询工作时才附带明确的工作语义，不需要手工复制上一位 Agent 的上下文。

用户不应该需要理解 Hub、账本、dispatch、API、环境变量或模型会话。

## 角色示例

- **World**：深度分析、复杂推理和制定方案。
- **Justice**：审查、验证、风险检查和提出反对意见。
- **Chariot**：按既定方案快速实现。
- **Fool**：由 Hermes 承担，保留它现有的能力和记忆。

这些角色不是硬编码的能力限制，Agent 的数量是部署决定而不是产品限制。用户可以直接
选择任何一个已配置的 Agent，也可以分别调整它们的模型、推理强度和速度。

## 基本体验

用户在协作群里新建一个话题，例如"支付模块重构"，然后说：

> @World 先深度分析这个问题，重点找架构风险，暂时不要写代码。

World 完成后，用户可以直接说：

> @Chariot 接着做。按照前面的结论实现，速度优先，不需要重新分析一遍。

Chariot 应该拿到继续工作所需的东西：

- 原始任务和用户后来补充的要求；
- 已确认的结论与决策；
- 关键证据、文件路径、提交和其他产物；
- 已完成事项、未完成事项和明确的下一步；
- 前序 Agent 创建或用户提供的文件，包括 PPT、文档、表格、PDF、图片和压缩包。

用户不需要复制 World 的回答，也不需要重新解释任务背景。Chariot 不能获得 World 的
私有思维链、临时工具输出、密钥或与任务无关的运行信息。

## 一段对话，按需携带工作语义

- **回复 / reply：** Agent 之间的普通群聊轮次，只授予一次可见、受授权的回复资格，
  不转移工作责任。
- **接手 / handoff：** 转移负责人和下一步目标。
- **咨询 / ask 与 return：** 请求局部帮助，负责人不变，结果回到当前负责人。
- **明确并行：** 用户真的同时 `@` 多个 Agent 时才并行唤醒。
- **完成 / complete：** 当前负责人带结论和产物收尾。

用户可以一次描述完整流程：

> @World 深度分析，方案确定后交给 Chariot 实现，完成后让 Justice 做一次审查。

Agent 之间的真实 `@` 是飞书里的可见通知，但只有协作系统里的正式转交才授权接手。
普通文字 `@` 或未经授权的互相唤醒不能触发任务，不会抢答，也不会形成循环。

## 顺序协作、咨询与并行

用户一条消息就能描述完整流程：

> @World 深度分析，方案确定后交给 Chariot 实现，完成后让 Justice 做一次审查。

理想的执行过程：

1. World 分析并在当前话题回复。
2. World 报告已转交，并在当前话题真实 `@Chariot`。
3. Chariot 收到结构化交接内容并完成实现。
4. Chariot 把结果和产物转交给 Justice。
5. Justice 要么把问题退回 Chariot，要么向用户报告完成。

在话题里显示"已转交给 Chariot"这类状态属于目标体验，bridge 目前还没有渲染它。

咨询不改变负责人：

> @World 继续负责这个任务，但让 Justice 只检查一下安全风险。

Justice 回答后，结果回到 World，负责人仍是 World。

只有用户明确同时 `@` 多个 Agent 时才广播或并行：

> @World @Justice 分别评估这个方案，一个看架构，一个看风险。

没有 `@` 的普通消息只补充当前话题上下文。多个机器人在同一个群里，不能对每条消息一起
回答。

## 上下文与状态

用户用自然语言表达范围："这条作为共享结论，后续 Agent 都要遵守"、"这段只给 Justice
做安全审查，不要传给其他 Agent"、"Chariot 只需要看最终方案和文件清单"。

代码现在强制执行的比这个意图更窄：消息默认是 task-public，`handoff` 对交接双方可见，
`ask` 只对被抓来咨询的 Agent 可见。`private-runtime` 和 `secret` 在协议类型和可见性
判断里存在，但还没有任何面向 Agent 的开关能产生它们；把用户的原话解释成范围指令，是
目标而不是已实现的能力。

这套权限首先是协作层面的。只要 Agent 以同一个 Windows 用户运行，它们在操作系统层面
可能访问相同文件；需要硬隔离就得用不同用户或容器。

每个话题应该给出简短、持续更新的状态，而不是让用户从长对话里自己拼：

> 当前负责人：Chariot
>
> 阶段：实现中
>
> 上一步：World 已完成架构分析
>
> 下一步：Justice 审查
>
> 共享产物：`design.md`、提交 `abc123`

状态展示是为了判断和操作，不展示内部协议、调试日志或思维链。现在的卡片显示的是运行
进度；上面这种"负责人/阶段/下一步"视图还是目标。

## 必须满足的验收标准

一个版本只有同时满足以下条件，才算实现了目标体验：

1. 用户在同一话题依次 `@` 两个 Agent，第二个能直接继续第一个的工作。
2. 第二个 Agent 能获得结论和产物，但不能获得第一个 Agent 的私有思维链。
3. Agent 能正式 `reply`、`handoff`、`ask`、`return` 和 `complete`，用户不需要搬运内容。
4. 未经正式授权的 Agent `@` 不触发任务，且不会形成机器人互相唤醒循环。
5. 没有 `@` 的消息不造成所有 Agent 抢答；同时 `@` 才表示明确并行。
6. 用户可以从飞书话题看出当前负责人、阶段、下一步和共享产物。
7. 完整历史仍可审计，但模型提示词只携带有界语义上下文；文件仅在本轮提及时按需取得。
8. Hub 或实验功能关闭后，现有桥接仍可按原方式独立运行。
9. Hermes 不被重装、不丢失原有状态，也不因协作层接入而改变现有命令和网关。
10. 任一 Agent 在任务中交付的文件或代码版本会成为有哈希、可见性和持久 locator 的
    共享产物，后续获准接手的 Agent 可以从 GitHub、飞书或配置的 provider 直接取得，
    不要求用户重新上传。

## 跨电脑部署方向

Agent 应能运行在不同电脑、不同用户或隔离执行环境中，而不改变用户在飞书中的协作方式。
用户仍然只需要在同一话题正常 `@`、查看交接和接收文件；Hub 地址、节点身份、文件下载
和断线恢复都应由部署与协议层处理。

这个方向已经有一部分在跑：`worker` 角色、每 Agent 独立凭据、远端 Hub 地址、节点与
实例身份、Hub 侧唯一任务真相都已实现，worker 节点也确实连着一台跑在别的机器上、通过
私网访问的 Hub。剩下的是加固：接收端自动下载产物、长时间断线后的恢复、凭据轮换、限额
和审计。能力状态与阶段验收（包括第二台机器的验收门槛）见
[跨电脑路线图](./DISTRIBUTED_DEPLOYMENT_ROADMAP.zh-CN.md)。

跨电脑不能以牺牲现有不变量为代价：Hub 仍是唯一任务真相，每个 Agent 仍使用自己的飞书
身份，真实通知仍需匹配正式授权，交付件仍需可追溯并按可见性授权。

## 实现必须坚持的方式

- 用户通过同一飞书话题自然完成选择、交接和咨询，系统自动搬运授权上下文；
- Hub 保存筛选后的共享任务状态，各 Agent 保留独立模型会话；
- 共享内容只包含任务事实、结论和产物，私有推理、工具噪声和秘密保持隔离；
- 正式所有权、dispatch 和路由由可审计协议保证，提示词只负责向 Agent 解释规则；
- Hub 维护唯一任务真相，各 Bot 从同一投影工作；
- 只有被真实 `@` 且取得授权的 Bot 响应，明确多选才并行；
- 每个 agent 拥有自己的 manifest、任务、凭据和本地账本，因此远端 worker 是增量能力，
  不改变单机使用方式；
- Hermes 通过可撤销适配保持原安装、状态、命令和网关；
- 飞书保持用户界面，内部协议和技术配置由系统承担。

## 开发决策原则

后续每项功能和重构都应回答三个问题：

1. 它是否减少了用户本来要自己做的事，比如在 Agent 之间搬上下文、手工管理 Agent？
2. 它是否让负责人、可见范围和下一步更清楚？
3. 它是否保持每个 Agent 都能单独使用、并且随时能回退？

任何一个答案是"否"，就需要重新审视实现方向。
