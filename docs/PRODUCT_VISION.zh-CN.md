[概念入门](./COLLABORATION_CONCEPTS.zh-CN.md) | [协作设计](./DESIGN.zh-CN.md) |
[Windows 运维](./WINDOWS_OPERATIONS.zh-CN.md) | [跨电脑路线图](./DISTRIBUTED_DEPLOYMENT_ROADMAP.zh-CN.md)

本文档定义这个项目最终要交付给用户的体验。架构、协议和代码可以演进，
但不能以牺牲这里的使用体验为代价。出现实现分歧时，以本文档作为产品判断依据。

## 一句话目标

用户只需要在飞书里像带一个四人团队一样工作：一个飞书话题就是一个任务，
`@` 哪个 Agent 就是选择或转交给哪个 Agent，不需要手工复制上一位 Agent 的上下文。

用户不应该需要理解 Hub、账本、dispatch、API、环境变量或模型会话。

## 用户看到的角色

- **World**：适合深度分析、复杂推理和制定方案。
- **Justice**：适合审查、验证、风险检查和提出反对意见。
- **Chariot**：适合根据既定方案快速推进和实现。
- **Fool**：由 Hermes 承担，保留其现有能力、记忆和使用方式。

这些角色不是硬编码的能力限制。用户始终可以直接选择任何一个 Agent，
也可以调整它们各自的模型、推理强度和速度配置。

## 基本体验

用户在四个机器人都在的协作群中新建一个话题，例如“支付模块重构”，然后说：

> @World 先深度分析这个问题，重点找架构风险，暂时不要写代码。

World 完成后，用户可以直接说：

> @Chariot 接着做。按照前面的结论实现，速度优先，不需要重新分析一遍。

Chariot 应自动获得完成当前工作所需的共享内容：

- 原始任务和用户后来补充的要求；
- 已确认的结论与决策；
- 关键证据、文件路径、提交和其他产物；
- 已完成事项、未完成事项和明确的下一步。
- 前序 Agent 创建或用户提供的文件，包括 PPT、文档、表格、PDF、图片和压缩包。

用户不需要复制 World 的回答，也不需要重新解释任务背景。Chariot 不应获得
World 的私有思维链、临时工具输出、密钥或与任务无关的运行信息。

## 顺序协作

用户可以一次描述完整流程：

> @World 深度分析，方案确定后交给 Chariot 实现，完成后让 Justice 做一次审查。

理想执行过程：

1. World 分析并在当前话题回复。
2. World 显示“已转交给 Chariot”，并在当前话题真实 `@Chariot`。
3. Chariot 自动收到结构化交接内容，完成实现。
4. Chariot 将结果和产物转交 Justice。
5. Justice 审查后，可以把问题退回 Chariot，也可以向用户报告完成。

Agent 之间的真实 `@` 是飞书中的可见通知；是否允许接手由协作系统里的正式
转交决定。普通文字 `@` 或未经授权的机器人互相唤醒不能触发任务，避免循环和抢答。

## 咨询而不转交

当前负责人可以请另一个 Agent 处理一个局部问题，但不放弃任务所有权：

> @World 继续负责这个任务，但让 Justice 只检查一下安全风险。

Justice 回答后，结果返回 World，当前负责人仍然是 World。

- **接手 / handoff**：当前负责人改变。
- **咨询 / ask**：目标 Agent 只回答指定问题，负责人不变。

用户不应为了完成一次咨询而手工把答案搬回原 Agent。

## 并行协作

只有用户明确同时 `@` 多个 Agent 时才进入广播或并行模式：

> @World @Justice 分别评估这个方案，一个看架构，一个看风险。

没有 `@` 的普通消息只补充当前话题上下文，不自动唤醒所有 Agent。系统不能因为
多个机器人在同一群里，就让它们对每条消息一起回答。

## 上下文可见性

用户应能用自然语言表达上下文范围，例如：

> 这条作为共享结论，后续 Agent 都要遵守。

> 这段只给 Justice 做安全审查，不要传给其他 Agent。

> Chariot 只需要看最终方案和文件清单，不需要看讨论过程。

系统需要区分：

- **任务共享**：参与当前任务的 Agent 可以看到；
- **交接内容**：交接双方可以看到；
- **定向内容**：仅指定 Agent 可以看到；
- **私有运行信息**：只属于当前 Agent，不进入共享上下文；
- **秘密信息**：不进入协作账本，也不通过 Agent 间交接传播。

这里的权限首先是协作层面的逻辑权限。只要 Agent 仍以同一 Windows 用户运行，
它们在操作系统层面可能访问相同文件；需要硬隔离时必须使用不同用户或容器。

## 用户看到的任务状态

每个话题应提供简洁、持续更新的状态，而不是要求用户从长对话中猜测：

> 当前负责人：Chariot
>
> 阶段：实现中
>
> 上一步：World 已完成架构分析
>
> 下一步：Justice 审查
>
> 共享产物：`design.md`、提交 `abc123`

状态展示应服务于判断和操作，不展示内部协议、调试日志或思维链。

## 必须满足的验收标准

一个版本只有同时满足以下条件，才算实现了目标体验：

1. 用户在同一话题依次 `@` 两个 Agent，第二个能直接继续第一个的工作。
2. 第二个 Agent 能获得结论和产物，但不能获得第一个 Agent 的私有思维链。
3. Agent 能正式 `handoff`、`ask`、`return` 和 `complete`，用户不需要搬运内容。
4. 未经正式授权的 Agent `@` 不触发任务，且不会形成机器人互相唤醒循环。
5. 没有 `@` 的消息不造成四个 Agent 抢答；同时 `@` 才表示明确并行。
6. 用户可以从飞书话题看出当前负责人、阶段、下一步和共享产物。
7. Hub 或实验功能关闭后，四个现有桥接仍可按原方式独立运行。
8. Hermes 不被重装、不丢失原有状态，也不因协作层接入而改变现有命令和网关。
9. 任一 Agent 在任务中交付的文件或代码版本会成为有哈希、可见性和持久 locator
   的共享产物，后续获准接手的 Agent 可以从 GitHub、飞书或配置的 provider 直接
   取得，不要求用户重新上传。

## 未来部署方向

Agent 最终应能运行在不同电脑、不同用户或隔离执行环境中，而不改变用户在飞书中的
协作方式。用户仍然只需要在同一话题正常 `@`、查看交接和接收文件；Hub 地址、节点
身份、文件下载和断线恢复都应由部署与协议层处理。

跨电脑不能以牺牲当前不变量为代价：Hub 仍是唯一任务真相，每个 Agent 仍使用自己
的飞书身份，真实通知仍需匹配正式授权，交付件仍需可追溯和按可见性授权。实现状态
与阶段验收见[跨电脑路线图](./DISTRIBUTED_DEPLOYMENT_ROADMAP.zh-CN.md)。

## 实现必须坚持的方式

- 用户通过同一飞书话题自然完成选择、交接和咨询，系统自动搬运授权上下文；
- Hub 保存筛选后的共享任务状态，各 Agent 保留独立模型会话；
- 共享内容只包含任务事实、结论和产物，私有推理、工具噪声和秘密保持隔离；
- 正式所有权、dispatch 和路由由可审计协议保证，提示词只负责向 Agent 解释规则；
- Hub 维护唯一任务真相，各 Bot 从同一投影工作；
- 只有被真实 `@` 且取得授权的 Bot 响应，明确多选才并行；
- Hermes 通过可撤销适配保持原安装、状态、命令和网关；
- 飞书保持用户界面，内部协议和技术配置由系统承担。

## 开发决策原则

后续每项功能和重构都应回答三个问题：

1. 它是否减少了用户搬运上下文和管理 Agent 的负担？
2. 它是否让任务所有权、可见范围和下一步更清楚？
3. 它是否保持现有四个 Agent 可独立使用并能随时回退？

三个问题中任何一个答案为“否”，就需要重新审视实现方向。
